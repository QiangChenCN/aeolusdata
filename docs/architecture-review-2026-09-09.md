# 工作台网页架构评估报告（2026-09-09）

> 评估对象：`index.html`（前端单页，5660 行 / 211 函数 / 单 `<script>`）+ `server.py`（后端，1723 行 / 手动路由链）。
> 评估维度：可维护性、结构清晰度、模块耦合度、扩展性、重复代码、导航耦合。

## 一、结论先行

**方向合理，实现需剪裁 —— 不需要推倒重写，但必须做针对性重构。**

你描述的「index 是独立网页、除首页外每个一级菜单相互独立」在**概念层**是对的、也适合这类内部工具；问题在于**实现层没有把这种「独立」落到代码边界上**：所有模块被压进同一个 ~5700 行的 HTML 文件和同一个 ~1700 行的服务器类里，共享全局 `state`、全局 CSS 和一套硬编码的导航/渲染分发。结果是「逻辑上独立、物理上耦合」。

因此建议：**保持单文件 SPA + 单服务进程的形态，不拆工程、不引框架**，只做内部边界治理。优先级见第五节。

## 三、分维度评估

### 1. 可维护性 —— ⚠️ 中低
- 单文件 5660 行意味着**任何一处编辑都可能影响毫不相干的模块**，没有模块隔离、无法单独测试、无法 tree-shake。
- 历史上已经出现过「并行 Edit 互相覆盖」「height/width 误改」这类典型的「巨文件」事故，正是该结构的副作用。
- 新人接手需先通读全文件才能改任何一处。

### 2. 结构清晰度 —— ⚠️ 中低
- 分层**只靠注释**，没有物理边界；渲染层注释写着「互不调用，统一由 refreshAll 调度」，但 `taskCard`(1589 起)→配置弹窗(3193)→多选站点(1911) 等约占 1800 行，全堆在同一层注释区间内，边界模糊。
- `python/dashboard/` 空目录 + 占位视图 = **悬空脚手架**，给人「即将有内容」的误导，属于结构噪音。

### 3. 模块耦合度 —— ⚠️ 中
- **导入期副作用导致被迫重复实现**：`python/jobs/attendance/attendance.py` 第 49–50 行在模块顶层 `os.makedirs(OUT_DIR)`；`server.py` 第 1339 行注释明说「在此自实现 teams 拉取，避免 import attendance（模块顶层会创建 out/ 目录，副作用）」。
  → 同一个「拉团队列表」逻辑在 attendance 与 server 里**各写一份**，且将来修 bug 必漏一处。
- **todo 双数据源**：SQLite 与 localStorage 克隆长期并存（迁移函数 `todoMigrateLocal` 被常驻在启动路径 3496）。迁移本应是一次性的，却变成了永久双路径。

### 4. 扩展性 —— ⚠️ 中
- 新增一个一级模块需要同时改 **≥3 处**：`navSections()`（导航）、`renderMain()` 的 if/else 链（分发）、`state` 初始化（数据切片）；若涉及后端还要再加端点。
- 导航与视图是**字符串硬编码**（`state.nav.kind` 取 `"home"/"tasks"/"dash"/"todo"/"history"/"hub"`），无注册表、无枚举，拼错即静默兜底到任务视图。
- `数据看板` 本是最自然的下一个模块，却因脚手架悬空而迟迟没接，侧面说明「加模块」的摩擦够高。

### 5. 重复代码 —— ⚠️ 中
- 后端 teams 拉取与 `attendance.fetch_teams` 同源但双写（见上）。
- 前端两个 fetch 封装：`api()`(1246) 与 `todoApi()`(3474)。
- 群选择两套实现：后端 `group_picker.search` + 前端 `mtp-*` 实时在线多选站点选择器（各自缓存/兜底）。

### 6. 导航耦合 —— ⚠️ 中
- `renderMain` 的 if/else 分发链与 `navSections` 的菜单结构**两处各自描述同一套模块**，新增模块必须两处同步，否则导航有入口却无视图（或反之）。
- 手风琴 `navExpandOnly` / `parentOn` 高亮逻辑与具体 `kind` 值强耦合，新增带子项的模块需理解这套特例。
- 本次「运行记录移入任务中心」之所以顺利，正是因为改动只动了 `navSections` 一处、且 `kind:"history"` 已被 `renderMain` 认领——说明**只要新增的是已有 kind，摩擦小；一旦新增 kind，摩擦陡增**。

## 五、重构建议（范围与优先级）

> 总原则：**不拆工程、不引前端框架、不重写**。只做内部边界治理，降低风险。

### 优先级 1（低风险、高收益，建议立即做）
- **P1 消重**：把 `attendance` 的 `OUT_DIR` 创建从「导入期」移到「真正写产物时」（函数内惰性创建），消除导入副作用；之后 server 直接 `import attendance.fetch_teams`，删掉内联重实现。一行副作用的挪动，换来一份逻辑唯一。
- **P2 收拾悬空脚手架**：`数据看板` 要么接一个最小真实视图（哪怕只读 `ods_delivery_tracking` 一张卡），要么**直接删掉空 `python/dashboard/` 与占位视图 + 一级入口**，停止误导。不要长期挂着空壳。

### 优先级 2（中等，解决扩展性核心）
- **P6 引入轻量「模块注册表」**：在 `index.html` 内用一张表 `{ kind, navMeta, init, render }` 替代 `renderMain` 的 if/else 与 `navSections` 的硬编码。新增模块只需注册一条，导航自动生成、分发自动覆盖。`state.nav.kind` 仍可用，但来源唯一。
- **P3 收口 todo 数据源**：确认迁移已完成后，移除 `todoLocalClone/todoDropLocal/todoMigrateLocal` 与启动路径里的迁移调用，只留服务端 SQLite 单一真相源。

### 优先级 3（较大、可选，看增长而定）
- **P5 后端职责拆分**：把 server.py 的端点按领域拆成 `handlers/` 小模块 + 一个小型路由注册表（仍然单进程、仍然原生 http），server.py 退化为组合根。仅在端点继续膨胀时做。
- **P4 前端是否分文件**：若坚持单文件则靠 P6 的注册表+命名空间(IIFE) 隔离即可；只有当单文件超过 ~8000 行或需多人并行改时，才考虑拆 `<script type="module">`。**不建议现在拆**。

## 六、维持现状的维护风险

1. **单点回归**：5700 行单文件下，一个手滑（如并行编辑覆盖、误改全局 CSS 变量）即可让整个工作台挂掉，无隔离兜底。历史上已发生同类事故。
2. **重复逻辑漂移**：teams 拉取、todo 双源这类重复，将来修一处漏一处，bug 复发且难定位。
3. **加模块摩擦高 → 功能被塞进巨石**：数据看板迟迟不接就是征兆；未来新需求会越堆越乱，技术债复利增长。
4. **新人/接手成本高**：任何改动都要先读懂全文件，故障排查需在 5600 行里翻找。
5. **测试不可行**：没有模块边界就无法单元测，只能靠整页手测，回归靠运气。

---

## 七、一句话总评

**架构方向（扁平、独立模块）没问题，但「独立」只停留在概念上；真正的风险是两份巨石文件 + 两处重复（teams、todo 双源）+ 一处悬空脚手架（数据看板）。先做 P1/P2 这两个半小时内能收掉的小重构，再排 P6 注册表解决扩展性，其余按需。现在不重构，债会越滚越大。**
